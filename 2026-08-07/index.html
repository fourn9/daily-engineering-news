Linux kernel の 18 年もの UAF SCTPhantom (CVE-2026-64564) が 8/6 に公開開示、8/7 に業界拡散。技術 = SCTP の Dynamic Address Reconfiguration 機能 の use-after-free、"DEL-IP 削除 の 検証 に packet の source address を使う一方、cached pointer は path 選択 の address parameter を使う" の identity mismatch、root 原因 の code は 2007年12月 の Linux 2.6.25 から存在。影響 = ローカル 非特権 ユーザ が root 昇格 + host escape、Tencent Zhuque Lab が Debian 13 / Ubuntu 24.04 / Rocky 9 / RHEL 9 / OpenCloudOS で root 取得 を実証、"local + SCTP reachable" が 前提条件。fix = stable branch 6.6.148 / 6.12.101 / 6.18.42 / 7.1.6 に backport、public exploit code は執筆時点 で未流通、CISA KEV catalog には未収載 (8/7 現在)。発見手法 = Tencent の "Corvus AI" 多エージェント kernel 研究 pipeline が発見、"AI エージェント が kernel の 未知 UAF を実際 に発掘" の 業界初 大型 事例。

🚨 業界警告: (1) 全 Linux ホスト を kernel 6.6.148 / 6.12.101 / 6.18.42 / 7.1.6 相当 以降 に patch、distro 側 の updated package (Debian / Ubuntu / RHEL / Rocky / OpenCloudOS) を 本日中 に schedule、(2) SCTP を業務 で 使わない host は modprobe -r sctp + blacklist で module を無効化 して 露出削減、(3) container escape 影響 のため マルチテナント Kubernetes / OpenShift / Docker host は 優先 patch、(4) Q4 の kernel patch 適用 SLA を "重大度 CVE = 7 日以内" に短縮検討、(5) "AI エージェント が kernel bug を発見する時代" の 前提 に 社内 kernel 診断 pipeline (Corvus 相当 の agentic fuzzing) の POC を Q4 R&D テーマ に。
💡読み手のための背景 — (1) "SCTP (Stream Control Transmission Protocol) とは": SCTP = TCP / UDP と並ぶ トランスポート層 protocol、"1 コネクション で 複数 stream" / "multi-homing (複数 IP を 1 endpoint で 束ねる)" が 特徴、"通信キャリア の SS7 over IP (SIGTRAN)"、"WebRTC の data channel"、"高信頼 ミッションクリティカル通信" で使用、"Web app 用途 では ほぼ使われない" が 一般認識、だが Linux kernel は デフォルト で SCTP module を load 可能 な状態、"module が有効 に なった 瞬間 に UAF が exploit 可能" が 落とし穴. (2) "use-after-free (UAF) の 攻撃価値": UAF = "解放済み memory を再度 使ってしまう bug"、kernel UAF は "memory 破壊 → 権限昇格 / RCE" の 最強クラス、"heap spray + type confusion" 等 の 定番テクニック で exploit 化、"local 権限昇格 → container escape → host RCE" の 直線、"Q3-Q4 の Linux CVE で 高影響度 の 常連 pattern". (3) "18 年 存在した bug を AI が 見つけた" の 業界インパクト: SCTP DAR 機能 は 2007年 の 追加 で 18 年間 人力 の code review / static analysis / fuzzing で 検出できず、Tencent Corvus AI = "多エージェント LLM pipeline が kernel code base を横断 read → 制御フロー を推論 → symbolic execution + fuzzing seed 生成 → PoC 実装" の 統合 workflow、"AI エージェント が 未知 kernel UAF を実際 に見つけ、PoC を作り、責任開示 まで 完走" の 世界初 級 の完成例、"agent が 攻撃側 (offensive security) の 主戦力 に" の Q4 業界共通認識、"防御側 の CodeMender (Google) / Rec-Sec AI (Anthropic) 等 と 対称的" の 構図. (4) "container escape" の 実運用重み: container = "root で走る namespace 隔離"、kernel UAF は namespace を突破 して host root に到達 する 経路、"1 container の 侵害 → node 全体 → k8s cluster 内 全 workload" の 横展開、Q4 の マルチテナント SaaS / Serverless / CI runner は "kernel patch cadence" が 事業リスク直結、"AWS Fargate / Google Cloud Run / Vercel Sandbox / Fly Machines / Cloudflare Workers gvisor" 等 の "強 isolation runtime" の 商業価値 が 再確認. (5) 読み手企業視点: (a) 社内 Linux fleet の patch 適用状況 を 本日 monitoring dashboard で 可視化、"SLA 7 日以内" の 達成率 を Q4 の SRE / infosec KPI に格上げ、(b) container runtime を "shared kernel 上 の Docker/containerd" から "強 isolation (gvisor / Firecracker / MicroVM)" に段階移行 の Q4 検討開始、(c) "AI agent が kernel bug を見つける" 前提 で 社内 kernel code / OSS 依存 の agentic vulnerability scan を Q4 パイロット、(d) SCTP module を全 host で 明示 disable ("SCTP を業務で使う host" が どこか の 棚卸 が第一歩)、(e) Board 資料 に "AI × セキュリティ の 攻撃 - 防御 加速" を Q4 経営 リスク として明示、"patch cadence 短縮 の budget" 要求根拠.

Uber が "exact COUNT(DISTINCT) を high-cardinality metric で スケール" の 設計 を 公開。問題 = "高次元 metric (rider ID / driver ID / session ID) は rollup で 統合 できず、"1 日 の unique rider 数" 相当 の 集計 が 素朴 実装 だと 数億 key を 常時保持"、"HyperLogLog (HLL) 等 の 近似 では 誤差 が 事業判断 に響く" の 実運用 課題. 解 = "partition-local な exact count + cross-partition の集約 pipeline" を "sketch-friendly な key encoding" と組合せ、"分散 exact COUNT(DISTINCT)" を線形計算量 に近づける、"HLL / Bloom / roaring bitmap" の 使い分け 表 と 実運用 数字 が articulate. 実装 = Uber の Real-time metrics platform (M3 + Pinot + Flink) 上 の pipeline、"1 日 の rider unique = 数千万" の 実 traffic で bench.

💡読み手のための背景 — (1) "COUNT(DISTINCT) が 分散 で 難しい" 理由: COUNT(DISTINCT) は "全 key を 集約 する必要"、"partition 別 に count しても "重複" が partition 境界 で 判定できない"、"1 partition = 1 億 key → 全 partition merge = O(N) memory"、"高頻度 の real-time 集計 では memory / network が 支配的" の 実装 pain. (2) "HLL / Bloom / roaring bitmap の 実運用選択": HLL = "log log 級 の memory で近似 count (誤差 0.5-2%)"、"Redis PFCOUNT / BigQuery APPROX_COUNT_DISTINCT" の中身、Bloom = "存在有無 の membership test に特化 (count 用途 でない)"、roaring bitmap = "整数 ID を bitmap 圧縮 で exact 保持、10 億 int を数 MB で"、"exact が必要 = roaring bitmap、近似で OK = HLL、membership only = Bloom" の 使い分け. (3) "rollup できない 生 metric" の 意味: rollup = "時間軸 / 次元軸 で 事前集計 (例: "1 分 count → 1 時間 sum")"、COUNT(DISTINCT) は sum できない (2 partition の distinct 合計 ≠ 全体 distinct)、"rollup 前提 の time-series DB (Prometheus / InfluxDB) が 弱い" の 典型パターン、"実装 は "全 key を 常時保持" or "近似で妥協" の二択". (4) 読み手企業視点: (a) 社内 の analytics で "unique user / unique session / unique transaction" 集計 を持つ場合、Q4 に "実装が HLL 近似 か exact bitmap か" を 棚卸、"事業判断 の 精度要求" と 対比、(b) "1 日 の active unique = ?" 相当 の 集計 は 実運用 で "近似 → 監査 で問題化" が 頻出 pattern、"監査対応 の 為 に exact 実装 に置換" が Q4 に散見、(c) roaring bitmap は OSS 実装 (Java / Go / Rust) 成熟、"HLL からの 移行" は Q4 の data engineering チーム の POC テーマ、(d) Uber の pipeline 設計 は M3 + Pinot + Flink の 特殊組合 が前提、"社内 stack (BigQuery / Snowflake / Databricks) での 相当 実装" は Q4 で adapt.
