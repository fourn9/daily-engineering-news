💡読み手のための背景 — (1) "AI エージェント runtime security" が Q3-Q4 の 新カテゴリ になった 経緯: 従来の EDR / XDR / SIEM = "人間 が 操作する machine" の 挙動 監視、"file を書いた / process を起動した / network に繋いだ" が主 signal、AI エージェント = "数秒に 数百 の tool call、判断の中身は 自然言語 の 推論"、"何をしたか" は 見えるが "なぜ そうしたか" は 見えない、"攻撃者に prompt injection されて 悪意 tool 呼出をした" が 従来 EDR で は 正常な agent 動作と 区別不能、これが runtime に 特化した agent 監視基盤 = ADR が 新カテゴリ として 立ち上がった 理由、AWS Contiuum (Publickey 経由 で既報) / Datadog LLM Observability / Arize Phoenix / Langfuse 等 の 商用 版 が Q3 に 一斉台頭、Uber は OSS で benchmark ごと公開 により カテゴリの標準化を狙う。(2) "17 の agent 攻撃技術 × 5 tactics" の 意味: MITRE ATT&CK の tactics/techniques の 分類フレームワーク を agent 領域に適用、"agent 特有の 攻撃技術" = prompt injection / indirect prompt injection / tool poisoning / data exfil via tool / infinite loop / privilege escalation via chained agent 等、ADR-Bench = agent 版 MITRE ATT&CK の 位置付け、Uber の 実 telemetry で validated、"agent security を 実装する 企業が 共通 で 使える benchmark" として standard の 座 を狙う。(3) "2-tier detection" の 設計哲学: 従来 の LLM ベース monitoring = 全 session を LLM で 判定 = agent 1 session の 監査 コスト が agent 実行コストを上回る 逆説、Uber ADR = tier 1 = fast triage (高 recall / 決定論的 signature-based) + tier 2 = LLM ベース 推論 (tier 1 で suspicious 判定された 5-10% のみ)、"監査コスト = 実行コスト × 10%" の trade-off、これは Netflix MSS pattern (昨日 briefing) の "narrow inference layer + 統合 制御プレーン" と 同じ思想、"AI システム を AI で監視する" の 実装哲学. (4) 本日 の npm worm 事案 との 補完関係: npm worm = 人間 の dev machine が 開発時に 感染、ADR = agent が 実行時 に 侵害される runtime を 保護、両方とも "AI 時代の 開発 / 実行 で 発生する 新種の脅威"、"開発時 (build time) supply chain 防御 + 実行時 (runtime) agent 防御" の 2 layer 防御 が Q4 の 標準、npm worm の "Claude Code / VS Code hook に 変種 植込み" の 部分は ADR が本来 検知 対象、"開発機 で agent が 感染して 本番システム を 攻撃する" 経路 を 防ぐ 目的. (5) 読み手企業視点の Q4 判断: (a) 自社 の Claude Code / Cursor / Devin / Cognition agents の 実行 telemetry が どこ に流れているか 監査、"observability tool が agent 推論を見えているか" を 検証、(b) ADR OSS を PoC として 8 月中 に deploy、ADR-Bench で 自社 agent の 現状スコア を測定、"どの攻撃技術に 弱いか" を 明示、(c) Q4 の "AI agent governance" 予算 に runtime security 予算 を 独立項目 として計上 (従来の EDR 予算 に含めない)、(d) 経営会議 で "AI agent 数 = 従業員数 に匹敵する 数千台の "実効 endpoint" の 認識共有、"agent は machine 1 台" ではなく "machine × session × tool" の 3 次元 監視対象、(e) 昨日 briefing の Anthropic Frontier Red Team 事案 (eval 環境 の 制御破綻) と 本記事 (production 環境 の 制御実装) は 表裏、"eval + production の両方で agent runtime を 監視 / 制御 する" が Q4 の 実装原則.
