昨日の 7/31 briefing でも取り上げた MCP 2026-07-28 spec の "stateless core" 転換が、週末 (8/1-8/2) にかけて 各エッジ / サーバレス プラットフォームの公式テンプレート化という第 2 波に入った。変更点の要点再掲 = bidirectional stateful → request/response の stateless モデルに変更、これで servers を サーバレス / エッジ で deploy 可能、任意の load balancer 背後で horizontal scale 可能、Apps / Tasks は versioned extensions framework で正式化、OAuth 2.0 / OIDC に完全準拠 (Entra / Okta と workaround なしで接続)。8/1-8/2 の週末 動向 = MCP SDK の月次 DL が 4 億 (前年比 4x)、Cloudflare Workers / Vercel Edge / AWS Lambda 上の "1-click MCP server テンプレ" が 各社ドキュメントに追加、"MCP server 開発 = Node/Python プロセスを常駐" 前提が崩れ "エッジ関数として書く" が新標準。

💡読み手のための背景 — (1) "stateless への転換" が実装コードに与える影響: 従来 MCP server = プロセス常駐で "セッション状態" を メモリ保持、これは agent との接続を切ると 状態消失 の制約、stateless 化で "各リクエストが self-contained、状態は外部 (DB / KV / cache) に永続化" が前提、コード的には Session を消して認証トークン + リクエストペイロードだけで完結する pure function 化、これで Cloudflare Workers (10ms cold start) / Vercel Edge (0ms cold start) 上に MCP server を deploy 可能、"1 リクエスト = 1 サーバレス関数呼出" になる。(2) "サーバレス / エッジ で deploy 可能" の 経済的意味: 従来 MCP server = 常時起動の EC2/GKE Pod = 100% コスト、stateless 化で 使用時のみ課金、多くの MCP server は "月に数十回しか呼ばれない社内ツール" のためこれで コストが 1/10-1/100 に、"社内 tool を全部 MCP 化して agent から使わせる" 意思決定の コスト障壁が消える。(3) OAuth 2.0 / OIDC 完全準拠の 意味: 従来 MCP = 認証を各自実装で エンタープライズ ID プロバイダ (Entra / Okta / Auth0) との統合に workaround が必要、これが 企業採用の 主要ブロッカーだった、stateless spec は OAuth 2.0 authorization code flow + OIDC を標準化、"IDP と MCP server を dropdown 選択で連携" が実現、CTO 視点で "MCP を情シスに通す" 障壁が消失。(4) "MCP Apps / Tasks の versioned extensions": MCP 元来は "tool call" だけを提供、Apps (interactive UI) / Tasks (long-running work) は 各社が spec 外で実装していた、これを 正式 extension framework 化、後方互換を保ちつつ 新機能 (例: agent が UI を返す、非同期完了通知を返す) を version 番号ごとに opt-in で追加 できる、"MCP 1.x で書いた client が 2.x server と共存可能" が実現、企業採用の 長期メンテナンス懸念が下がる。(5) Q4 の実務判断: (a) 社内 MCP server の 8-9 月中 stateless spec 移行の PoC (エッジデプロイ orbit で コスト検証)、(b) MCP server の 認証設計を "自前 API key" から "OAuth via 社内 IDP" に切替、(c) 長期タスク (build / test / deploy 系 agent workflow) を Tasks extension で書き直す、(d) 昨日 briefing の JetBrains Context (repository intelligence) と Cloudflare Local Explorer と組合わせ "エッジで agent + repo intel + tools" の三層 architecture を Q4 参照実装に。

AirLLM が GitHub Trending #3 に浮上、本日 +963 stars/day の急上昇。設計思想 = 非量子化・非蒸留・非プルーニングで 70B → 405B → 671B → 2.8T の frontier open weight model を 4-12GB VRAM で 単一 GPU / MacBook で動かす、layer-wise inference の thoroughgoing 実装。2026 の 主要 update = 7 月に Kimi K3 (2.8T パラメータ) 対応、RTX 6000 Ada 単体 3.72GB VRAM で end-to-end 動作を実測、Llama 3.1 405B が 8GB / DeepSeek-V3 671B が ~12GB / Qwen3-235B が ~3GB (v3.0 で FP8 model 対応、2026-06)。本日の急上昇 = 7/31 の Simon Willison × Oxide and Friends podcast で "Kimi K3 が proprietary frontier に競う証拠" と言及されたのが 拡散のトリガ、月間累計 +66K stars で "single-GPU frontier open weight" カテゴリの de facto。

💡読み手のための背景 — (1) "非量子化で 2.8T パラメータを 4GB VRAM" は理論的にどう可能か: 普通 2.8T パラメータ (FP16) = 5.6TB の VRAM が必要、これを 4GB に押し込むのが不可能に見えるカラクリ = layer-wise inference = "推論時に必要な 1 layer だけを VRAM に load → forward pass → 次の layer に置換" を繰り返す、これで peak VRAM = 単一 layer 分に激減、代償 = ディスク I/O が推論時間を支配、実測レイテンシは 数秒/token レベル (proprietary API の 数十 ms/token とは桁違い)、"インタラクティブ用途 ではなく バッチ inference / エッジ実装" が真の use case。(2) "量子化・蒸留・プルーニングを使わない" の 意味: 普通 open weight を単一 GPU で動かすには INT4 / INT8 量子化 (精度低下)、distillation (小型モデル再学習)、pruning (パラメータ削減) を 使う、AirLLM は "オリジナル重み を loss なしで そのまま動かす" ため proprietary API と全く同じ output を得られる、"open weight ≠ 精度劣化" を実証。(3) "Kimi K3 (2.8T)" とは: Moonshot AI (中国) が 2026 前半に 公開した open weight frontier model、2.8T パラメータで GPT-5 / Claude Opus 5 と benchmark 上競う、Simon Willison が "open weight でも proprietary frontier と競えるようになった Tipping point" と 認定、Anthropic / OpenAI の "moat" が モデル重みではなく infra / tooling / distribution にシフトしている 傍証。(4) 実務での使われ方: (a) Air-gapped 環境 (医療 / 金融 / 政府) で frontier model を 単一 workstation で運用、(b) バッチ推論 (夜間 doc processing / research pipeline) で API cost を ゼロに、(c) エッジ検証 (単一 MacBook で prompt engineering) を frontier model で行う、読み手企業視点: 自社の 秘匿データ (医療 / 契約 / M&A) を "API に送らずに frontier で処理" が 8 月末までに 実現可能に。(5) 他 OSS 実装との比較: llama.cpp = 幅広いモデル対応 + 量子化前提、AirLLM = frontier open weight 特化 + フルプレシジョン、ollama = local model の パッケージング、vLLM = throughput 最適化 (server 用途)、"AirLLM は "小さい GPU でも フルプレシジョン" が唯一の 差別化"、antirez の ds4 と同じ "narrow scope で最深最適化" 哲学。

💡読み手のための背景 — (1) "vibe coding" とは何か: Andrej Karpathy が 2025 に 命名した用語、"要件を正確に書かず、雰囲気で AI に投げ、出力を試して修正を繰り返す" コーディングスタイル、短期的には 1 人月の作業 が 1 日のような 劇的短縮を達成、しかし中長期で "コンテキストがチャット履歴に散逸 → 誰も全体を把握していない → 保守できない" の 3 種消耗が発生、業界で "Q3 2026 に vibe coding 疲労" 現象が観測された。(2) "SDD (Spec-Driven Development)" とは何を置き換えるか: 従来の TDD (test-first) や BDD (behavior-first) と 似た path、SDD = spec.md を single source of truth にし "コード ← spec、spec ← 会話、会話 ← 仕様意図" の 4 層を明示的に維持、AI エージェント が spec.md を 読み書きする primary artifact として扱う、"AI コーディング時代の 版管理" と言える、GitHub Spec-kit (spec-driven scaffolding) や tsumiki (Claude Code SDD ツール) が 実装、Karpathy vibe coding の 反対極として 定着。(3) "1 Todo = 1 Commit = 1 Spec Update" 原則の 意味: 従来 = "1 commit に 複数機能、spec は README 等に断片的"、SDD = 各 commit は 単一 Todo に対応、各 Todo は spec.md の 1 セクション更新を含む、これで "3 ヶ月後に なぜこの実装になったか" を git log + spec.md の diff で 完全再構成できる、"AI に修正させる時も spec.md を context として渡せば 過去の意思決定と 矛盾しない"。(4) 昨日 briefing 記事との 関係: 昨日 (2026-08-01) 掲載の 国内 AI エージェント動向 記事 (Yasuhito Morimoto) の "権限 5 要素 runbook (差分確認 / undo / 最小権限 / log / KPI)" と SDD は 補完関係、SDD が "作る側の gouvernance"、Morimoto runbook が "動かす側の gouvernance"、2 つ揃って "AI を使う vs AI に統治される" の分水嶺の 実装レイヤ。(5) 読み手企業視点の Q4 判断: (a) 社内 Claude Code / Cursor 使用チームに SDD 実践ガイドを Q4 の 標準プラクティスとして 導入、"1 Todo = 1 Commit = 1 Spec Update" を レビュー基準に、(b) VSDD Claude Code プラグインを Q4 内 で PoC、SDD + TDD + VDD の 三重ゲートを 一部 チームで試験導入、(c) Github Spec-kit を 新規プロジェクトの scaffolding として 標準化、Q4 の 新規プロダクト から 開始、(d) 開発時間 27-43% 削減 / バグ 71-83% 削減 の 実測値は "AI 導入 ROI" の 説得材料として 経営会議に持ち込む価値大、(e) tsumiki / cc-sdd などの ツール比較検討を Q4 の 技術書 club or engineering AllHands の 議題に。
