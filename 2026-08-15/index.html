🛠 Claude Code / エージェント運用

Claude Code v2.1.230→232 — subagent forking 既定 ON・セッション間メッセージング・GitLab plugin marketplace が同一週にまとめ投入

🔥話題Claude Code仕様変更
出典: Anthropic Claude Code Docs Changelog（v2.1.230 / v2.1.231 / v2.1.232、2026-08-14〜08-15）

昨日の auto-mode 既定化 (8/14) の翌日に Anthropic は 3 リリースで CLI を並列 agent 前提に組み替え。主なもの: (1) subagent forking が既定 ON ─ 派生 agent が親の 会話履歴と prompt cache を継承し、"数珠繋ぎの並列 agent" を context の断絶なしに走らせられる、(2) クロスセッションメッセージング ─ 別の Claude Code セッションから話しかけると受信ダイアログ (accept / hold / refuse) が出る、/config に "Dialog expiry" と "Messages from your other sessions" 行が追加、(3) GitLab plugin marketplace ─ gitlab.com の bare URL (nested subgroup 込み) が github.com URL と同等に clone 可能、clone auth 失敗ヒントも実際の git host 名で出る、(4) Worktree 隔離の強化 ─ subagent が git -C / --git-dir / GIT_DIR で共有 checkout を触れなくなり、Bash とファイル編集の隔離が全セッション型に適用、(5) Linux 側 memory cgroup 対応 ─ CLAUDE_CODE_TOOL_MEMORY_LIMIT で暴走 build がセッションを止めない、(6) GitLab トークン (glrt-, gloas-, glptt-, glagent- 等) の secret redaction 追加、(7) 長時間 thinking 中でも SSE keepalive ping を Vertex / Bedrock upstream に送って idle-timeout 切断を防止、(8) fullscreen streaming で会話全体の re-normalize を廃止し長セッションの応答性改善、など計 49 変更。

💡 背景補足: Claude Code は 2.1.221〜228 で "1 CLI 内の tool permissioning" を仕上げ、昨日 8/14 の auto-mode 既定化で "コマンド単位の許諾" を classifier に譲った。次に来たのが今回の "セッション同士を繋ぐ" レイヤで、要点は agent の粒度が "1 対話 = 1 セッション" から "session mesh" に移ったこと。cross-session messaging は "別ターミナルの Claude に頼み事を投げる" (== agent-to-agent A2A の同社内実装) で、subagent forking の cache 継承と組み合わせると "並列 agent が同じ context を共有しつつ独立に走る" 開発フローが素で組める。GitLab plugin marketplace 一級対応は、Enterprise 移行時の "GitHub 一択" 前提を崩す実務的な調整。読み手の示唆: (a) subagent 既定 ON によって context / cache のコストが暗黙に増えるため、社内で "1 タスク = 1 セッション" のコスト前提を再測定するタイミング、(b) cross-session messaging は知らずに別セッションから干渉される攻撃面 (prompt injection の bridge) が広がる — Dialog expiry と Messages from your other sessions を早めに社内ポリシーで既定 "hold" に、(c) worktree 隔離が Bash と file edit まで拡張されたので、社内のカスタム "全部通し" MCP tool は仕組み上の再点検が必要。

cordiverse/cordis — "Meta-Framework of Spatiotemporal Composability" が DeepSeek Harness の plugin kernel に採用、Koishi bot で 4 年の実運用を経て "agent の外側 OS 層" として再登場

📐設計論🛠OSSエージェント基盤
出典: GitHub cordiverse/cordis（Trending Today +616 stars、累計 3,994 stars）/ floatboat.ai 解説記事

TypeScript 製の Meta-Framework of Spatiotemporal Composability。中核の主張は「software component は 空間 (どの plugin が active か) と時間 (いつ mount / unmount するか) の両方で composableであるべき」で、これを effect tracking + coeffect resolution + hot module replacement + reconciliation-based loader として実装する。Cordis 自身は 2022 年に始まり、Discord/Telegram/LINE 横断のクロスプラットフォーム chatbot フレーム Koishi の kernel として 4 年間本番運用されていた基盤。今週 (2026-08-13) 公開の DeepSeek Harness Developer Preview がこの Cordis v4 を plugin kernel に採用したことで、"chatbot 用の低レベル部品" から "agent OS の plugin layer" として再ラベルされ、GitHub Trending に急浮上 (今日 +616 stars)。API はまだ stable ではなく、predicted に変更あり得ると明記。MIT。

💡 背景補足: "agent OS の plugin layer" は Google Skills、Anthropic の subagent、Cloudflare Agent SDK、holaOS (昨日) など各社がそれぞれ実装しているが、いずれも "自社 CLI の内側部品"。Cordis の面白さは (i) chatbot 由来の 4 年運用で "plugin の再入 / hot reload / 依存の DAG 解決" という現代 agent が抱える問題を先に解いていたこと、(ii) それを meta-framework = OS 外側から差し込める形で切り出していること、(iii) DeepSeek Harness という 2026 年ベンチマークで benchmark 用ハーネスが逆に OSS 化する 新しい流れに乗ったこと。用語補足: spatiotemporal composability は "同じ機能を空間 (どの plugin 集合か) と時間 (いつ有効化するか) の 2 軸で組み替えられる" 性質で、"実行中に plugin を差し替えても状態を失わない" という要件のことを指す。応用エッセンスは、社内で複数の agent framework (Claude Code + Codex + 内製) を並走させる場合、各 CLI 内側で plugin を書くのではなく、外側の meta-framework (Cordis 相当) を先に決めて plugin を移植可能な単位で切ると、フレームワーク乗り換えコストが劇的に下がる。同日の Claude Code cross-session messaging と併読すると、"agent 内部設計 → agent 間プロトコル → agent OS 層" の 3 層が独立に商用化されつつある。

Cloudflare cdnjs、Developer Platform 全体 (Workers / R2 / KV / Workflows / Queues / Durable Objects / Containers) への移行を完了 — 9B req/day、98.6% cache hit の dogfooding 事例を InfoQ が 8/14 に整理

📐設計論クラウド
出典: InfoQ「Cloudflare Migrates JavaScript CDN Serving 9B Requests a Day」（2026-08-14）

Cloudflare が JS / CSS ライブラリ CDN の cdnjs を、自社 Developer Platform 上に完全移行済 (現行 GA)。アーキテクチャは Workers (serving) + R2 (source of truth) + KV (metadata / SRI hash / version) + Workflows / Queues / Durable Objects / Containers の組み合わせで、Workers Cache が前段。数字は 9B req/day / ピーク 108K req/s / 330+ データセンタ / 98.6% cache hit、影響範囲は "全 Web サイトの約 12%" が使用。設計上のトピック 3 点: (1) R2 が単一 source of truth ─ KV に載らなかった source maps / 大 bundle / font pack を扱えるように、(2) DigitalOcean Spaces にライブ mirror ─ 単なる DR ではなく "R2 が失敗したら serving Worker が読みに行く live fallback"、キャッシュ→R2→DigitalOcean の 3 段チェーン、(3) URL / SRI hash / package 内容を一切変えずに移行し切り、後方互換を維持。Cloudflare 側の位置付けは "Developer Platform の dogfooding at scale"。

💡 背景補足: "全部自社 primitive で書き直す" 系の事例で見るべきは failover と移行手順で、この cdnjs はその両方が教科書的に整理されている。特に DigitalOcean Spaces を "外部 vendor に置いた live fallback" にする設計は、"single vendor 最適化と blast radius 制御" のトレードオフを "全乗せしつつ、ホット・スタンバイだけ他社に外す" という具体例で回答したもの (自社 primitive の障害と自社 platform 全体の障害を切り離せる)。位置付け: (i) DR (Disaster Recovery) は "冷たいバックアップ"、live fallback は "常時パスに入る二重化" で、後者は運用コストがかかる代わりに切替時間ゼロ。(ii) URL / SRI hash 不変移行は SRI (Subresource Integrity) を採用している下流サイトの完全性検証を壊さないための実務条件で、SRI は "指定した hash と一致しないと script を実行しない" ブラウザ機能。応用エッセンスは、社内で "自社 platform に大規模サービスを載せ替える" ときに (a) 外部 vendor に live fallback を残す、(b) 下流に露出している identifier (URL / hash / etag) を 移行前後で bit-identical に保つ、この 2 点は自社規模でも移植価値が高い。

citrolabs/ego-lite — "ログイン state を継承したまま agent に渡すブラウザ"、Claude Code / Codex から並列 Space で web 自動化 (Trending Today +546)

🆕新リリース🛠OSSエージェント基盤
出典: GitHub citrolabs/ego-lite（Trending Today +546 stars、累計 10,871 stars、MIT / macOS 先行）

"agent 向けに最速の web 自動化ブラウザ" を掲げる OSS。設計上のヘッドラインは 3 点: (1) 自分がログインしている Cookie / Session を agent 側に そのまま継承させ、GitHub / Jira / 社内管理画面等をパスワード or API key なしで叩ける (== login state pass-through)、(2) Spaces: 1 ブラウザ内の並列 workspace で、各 Space が独立 agent タスクを保持、"Claude Code が 10 Space でリード拡充・Codex が 5 Space で競合スクレイピング" が衝突なしに走る、(3) 連携層 ego-browser が Claude Code / Codex / Cursor / 自作 CLI に統一 JS tool (snapshot / fill / click / wait / navigate / capture) を露出し、agent は 1 回で JS スニペットを流し込むだけ。macOS 先行、Windows / Linux は roadmap。

💡 背景補足: 現状の agent-x-Web の主流は Playwright / Puppeteer 系の "clean profile で立ち上げて手動で login させる" か、Anthropic Computer Use 系の "画像 + マウスで OS を操作する" のどちらか。ego-lite は "人間が既にログイン済みのブラウザプロファイルを、agent と共有する" という第 3 の道で、"社内サービスに OAuth 設定不要のまま agent が入れる" 実運用の摩擦を大きく減らす。反面、副作用は "agent が誤って本人アカウントで書き込む" リスク — この点を Space 単位の隔離で分離しているのが設計要諦。読み手の示唆: (a) 社内で "1 人のブラウザから複数 agent が同時に社内 SaaS を叩く" 運用は ログ帰属と rate limitの再設計が必要、(b) ego-lite 型 UX を採用する場合、"どの Space から何ができるか" の permission gate を各 SaaS 側で書けるか (== agent-aware ACL) が今後の SaaS ベンダー競争軸に。同日の Claude Code cross-session messaging と併せ、"agent 間の暗黙のブリッジ点" が session / browser 両側で増えたのが本日の設計傾向。

HKUDS/CLI-Anything — "全てのソフトを agent-native に" GUI アプリを CLI 経由で agent 操作可能にする plugin + hub、Claude Code plugin 同梱 (Trending +100)

🆕新リリース🛠OSSエージェント基盤
出典: GitHub HKUDS/CLI-Anything（Trending Today +100 stars、累計 47,286 stars、香港大 Data Intelligence Lab）

香港大 Data Intelligence Lab (HKUDS) が公開した agent-native CLI 生成器。仕組みは 3 段: (1) 既存 GUI アプリのアーキ解析、(2) GUI 機能を鏡写した CLI 設計、(3) 状態管理・undo/redo・REPL・JSON 出力を含む stateful CLI の実装。生成された CLI は API / GUI 再構築 / 複雑な wrapper 一切不要で agent に操作させられる、というのがヘッドライン。同 repo は Claude Code 用 plugin (cli-anything-plugin) を同梱し、公開カタログ (clianything.cc) に "pre-built agent-native CLI" が並ぶ。

💡 背景補足: agent が現世の GUI ソフトを触るには (i) 画像 + マウス操作 (Anthropic Computer Use / OpenAI Operator)、(ii) native API / MCP server 経由、(iii) 独自の RPA、の 3 択が今の主流。CLI-Anything は "agent が使う interface として CLI を第一級にし、既存 GUI をそこに落とす" 4 番目のアプローチ。ポイントは "REPL / JSON 出力 / undo-redo / full test coverage" の 4 点を要求している点で、これは agent が誤操作しても復帰できる ACID 相当の CLI 契約を先に固めているということ。応用エッセンスは、社内ツールを "agent に触らせる" 前に、MCP server を書くより先に "冪等な CLI + JSON 出力 + undo 可能な state" の 3 点を先に決めておくと、後で MCP でも A2A でも下位互換が効くこと。同日の ego-lite (login state pass-through) と併せ、"agent の interface 層を 3 種類 (Browser / CLI / API) 揃える" 動きが今週の trending の底流。

sqliteai/waste — Kimi K3 (2.78T パラメタ) を 64GB MacBook で走らせる C 製 inference engine、NVMe から expert を streaming する MoE 特化ラン

🛠OSSローカル推論MoE
出典: GitHub sqliteai/waste（HN 話題継続、Trending 済み、MarcoBambini Substack 解説）

"Weight-Aware Streaming Tensor Engine" (略 WASTE) の名でリリースされた 依存ゼロ・組込み可能な C 製推論エンジン。目的は Moonshot AI の Kimi K3 (2.78T) を消費者ハードで走らせること。設計要諦: (1) モデル本体 (~27GB) は RAM に residing、(2) MoE の 1 トークンあたり活性 expert (全体の ~4%) だけを NVMe から streaming、(3) 残りの RAM を expert cache (bounded) として使う、(4) expert は 3-bit / 本体は 4-bit + 8-bit 量子化、(5) 全 layer / 全 expert を "蒸留も pruning もせず" 保持。実測 64GB MacBook Pro M5 Pro で 0.49-0.54 tok/s、ストレージ約 1TB を消費。ViT (27 層) による multimodal 入力と OpenAI 互換 HTTP サーバも同梱、macOS/Linux/Windows 対応、BLAS/CUDA/ONNX/Python 依存なし。

💡 背景補足: MoE (Mixture of Experts) は "毎トークン全部のパラメタは使わない、担当 expert だけ活性化する" 系のモデルで、これを NVMe streaming に切り出せる可能性は理論上前から言われていたが、"消費者 SSD の帯域で GPT-4 級 MoE が走る" 実測は本作が最も広く共有された事例のひとつ。用語補足: expert cache は "直近使った expert 集合を RAM に留める LRU 相当" で、活性 expert の再使用局所性 (== 会話が続くとルーティングが安定する現象) に賭ける設計。0.5 tok/s は "対話には遅い" 水準だが、意義は速度ではなく "trillion-scale MoE のフル weight が個人の Mac に載る" という設計の存在証明。応用エッセンスは、(a) MoE モデルは "実質サイズ = 本体 + 活性 expert 平均" でメモリ計画すべきというプランニング指針が確定した、(b) 社内 offline / 機密環境で "全 weight を可搬デバイスに載せる" 要件がある場合、MoE アーキ + NVMe streamingが量子化以上に効くケースが出始めた点。

🔬 論文 / 研究

Externalization in LLM Agents — memory / skills / protocols / harness の 4 層で "モデル内側にあった機能を外側に切り出す" 設計論の systems-level フレーム (Unified Review)

🔬論文📐設計論エージェント基盤
出典: arXiv:2604.08224（Chenyu Zhou ほか、2026-04 公開・以降 update、systems-level review）

初期の LLM agent は "モデル内側に知識・記憶・スキルを閉じ込めて解く" だったが、実務は "モデル外側に memory 層 / reusable skill / interaction protocol / harness を並べ、モデルはそれらを orchestrate する" 方向へ移った、という観察を 4 層の外部化 (externalization) フレームで統一 review した論文。要点: (i) Memory は "時間軸で state を外部化する層" (vector store, working memory, episodic recall)、(ii) Skills は "手続き知識を再利用可能な形に外部化" (Anthropic の Skills / OpenAI GPT Store 的アプローチ)、(iii) Protocols は "agent 間・agent-tool 間の interaction 構造を外部化" (MCP / A2A / OpenAPI 契約)、(iv) Harness engineering は "これら 3 つを governed execution として束ねる統合層" (== Claude Code / Codex / DeepSeek Harness などの CLI 側)。結論として "モデルサイズを増やす" より "4 層の外部化を洗練する" ほうが実用 agent の伸びしろが大きい、と主張。

💡 背景補足: 本論文の意義は "MCP / Skills / harness engineering / long-term memory を 1 枚の設計図に載せた最初の unified review" である点。特に読み手の関心領域と接続する 3 点: (a) harness engineering という用語を正当に定義している (Claude Code や Cursor CLI のような "外側の runtime + policy 層" が独立した工学領域として明示された)、(b) MCP は "Protocols 層" の 1 実装という位置付けで、A2A や OpenAPI 契約もここに合流する、(c) memory と skill の分離が実務では曖昧になりがちだが、"時間軸に State を伸ばす vs 手続きを再利用する" と役割で切ることを提唱。応用エッセンスは、社内 agent 導入時に "モデル選定" を 1 議題にしがちだが、実際は Memory / Skills / Protocols / Harness の 4 層で "誰が何を owner に持つか" を先に決めるほうが総合コストが下がるという設計指針。本日の Claude Code cross-session messaging (Harness 層 の拡張)、Cordis (Protocols 層 の外部化)、CLI-Anything (Skills 層のバックエンド化) は、それぞれ本論文の 4 層のうち別の層を動かしており、今週の trending を "この論文のどの層が動いているか" で読むと構図が整理される。

日本の AI エージェント市場の隔週レビュー最新号。要旨は「競争軸は 単一モデルの回答精度 → "どの業務データに、誰の権限で、どこまで完結して繋げるか" に既に移った」。実装が縦割りで進んでいる領域として 営業・薬事解析・カスタマーサポート・コード移行・インシデント対応・経理・EC を列挙。共通の設計パターンは 4 つに収れんしつつある: (1) 権限 pass-through (GAIA)、(2) 監査ログ、(3) 例外提示 (kozokaAI)、(4) 使用ルール判定 (TOKIUM)。導入企業側が個別に検証すべき軸として 自動書き込み範囲・承認ゲート・失敗時リトライ・監査ログ・定量 KPI の 5 点を挙げる。将来的な勝ち筋は "モデル性能" ではなく "安全な権限設計 + 既存システム連携 + 導入後の改善サイクル" を回せるベンダーに移る、と結論。

💡 背景補足: 本記事の重要性は "国内 AI エージェント市場を vertical 単位で並べて設計パターン化した最新のスナップショット" である点。国内特有の観察は 3 点: (a) 業務ドメイン (経理・薬事) 毎に 権限 pass-through をどう表現するかが業界ごとに違う (SAP や電子帳簿保存法との整合)、(b) 監査ログは "コンプライアンス要件" ではなく "AI の説明責任" として設計軸になり始めた、(c) 例外提示 (kozokaAI 型) は "自動処理は 80% 通し、20% を人間に返す" ハイブリッド運用の共通言語になっている。海外の Claude Code auto-mode の "classifier に許諾を移譲" とちょうど対を成す議論で、日本側は "許諾は人に、記録は agent に" 側に寄っている。応用エッセンスは、社内で AI エージェント PoC を進めるチームが、モデル選定より先に 権限 pass-through の実装方式・監査ログのスキーマ・例外提示 UX の 3 点を "ベンダーに丸投げできない自社決定事項" として先に固めるべきという実務的指針。同日の Claude Code cross-session messaging と読み合わせると、"agent 間の権限伝播" は国内も海外も 2026 秋の重要議題。
