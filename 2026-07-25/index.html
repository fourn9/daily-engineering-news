The 2026-07-28 MCP Specification Release Candidate (Model Context Protocol Blog / 2026-07-23) — launch 以来最大の改訂、stateless core / Extensions / Tasks / MCP Apps / Enterprise Auth stable、月曜 (7/28) 最終仕様 ship 予定

🔥話題🆕新仕様MCPagent 基盤
出典: blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate (2026-07-23 RC 公開 / 7/28 final ship 予定)

MCP の 2026-07-28 仕様 RC が公開。launch 以来最大の改訂で、(a) protocol core が stateless 化 (initialize/initialized のハンドシェイクと Mcp-Session-Id ヘッダを廃止、per-request の Mcp-Method / Mcp-Name ヘッダでリクエストがどの server instance にも当たれる)、(b) Extensions framework 新設で "MCP Apps" (server-rendered UI 配布) と "Tasks" (long-running work) が最初の 2 拡張、(c) OAuth / OpenID Connect と整合する authorization hardening、(d) Enterprise-Managed Authorization extension が stable 昇格 (IdP 経由の一元アクセス管理)、(e) 正式な deprecation policy。public MCP server 10,000+ 稼働 / SDK 月間 97M+ DL の規模で、final ship まで残 3 日、SDK maintainer と client 実装者に 10 週間の validation window。

💡読み手のための背景 — (1) "stateless 化" が運用に与える破壊的インパクト: 旧仕様は "client と特定 server instance が sticky session を張り、Mcp-Session-Id で紐付ける" 前提で、負荷分散側で sticky routing (source IP hash / cookie) が必須、水平スケール時は session 情報を Redis 等の共有 store に載せる必要、gateway で MCP メソッド判定のため deep packet inspection が必要だった。新仕様では per-request ヘッダ (Mcp-Method / Mcp-Name) がリクエスト内容を宣言し、"どのインスタンスがどのリクエストを処理できるか" を LB が上位層で判定可能。結果: 素の round-robin LB の背後で MCP server を運用でき、Redis 共有 store も要らず、tools/list のような読み取り系は server 側 ttlMs 内で client キャッシュ可能。読み手企業で MCP server を production 運用している場合、Q3 中に "sticky routing 依存箇所と共有 session store" の廃止計画を組む価値。(2) "Extensions framework" と 2 拡張の意義: (a) MCP Apps = server 側で render した UI (フォーム、テーブル、ダッシュボード) を agent の会話コンテキストに埋め込める仕組み。従来の text-only 会話から "server 提供の rich UI で人間の入力を得る" フローが可能。GitHub Copilot の canvas (7/24 briefing) や ChatGPT Apps / Anthropic Artifacts と接続する下位層規格。(b) Tasks = long-running work の第一級表現。従来は "1 リクエスト = 1 完了" 前提で、数分〜数時間の tool 実行を扱いにくかった。Tasks 拡張で "起動 → poll → 途中経過通知 → 完了" の共通プロトコルを標準化 = 読み手企業の "batch job や CI job を agent から起動する" 実装が MCP 標準の上で書ける。(3) "Enterprise-Managed Authorization stable 昇格" の実務含意: 従来 MCP server ごとにアクセス制御を実装 → 企業内で "誰がどの MCP server の何ツールを使えるか" が一元管理できず、監査対応が破綻。Enterprise Auth extension は Okta / Azure AD / Auth0 等の IdP を "MCP server 群への統一入口" として立てる仕組み。読み手企業で "10+ の MCP server が乱立" 状態なら、この extension を採用して Q3 中に IdP 経由の一元化が現実的。(4) "tools/list キャッシュ可能" が示す性能改善: 従来 MCP client は "会話開始時に tools/list を毎回叩く" 必要があり、agent の初回応答の latency ペナルティ。新仕様の ttlMs で server が "この tools リストは N ms 有効" と宣言できる = client 側 CDN / メモリキャッシュ可能。(5) Fowler (7/21) との接続: 「harness engineering」の "protocol 層" の完成度が MCP でここまで上がった = 読み手企業が 2026 後半に自作する agent は「MCP を trans-service 通信の第一選択」に据える判断がより正しくなった。(6) 7/28 (月曜) の具体アクション: (a) 本日〜月曜で "自社の MCP client / server に sticky session 前提や session_id 依存があるか" を grep 探索、(b) Enterprise Auth extension の Okta / Azure AD 連携ガイドを月曜 to 火曜で試験、(c) Q3 中に "従来仕様 (stateful) と新仕様 (stateless) の 2 モード両立" を計画。

Atlassian が Jira に "AI-native SDLC" 機能群を実装。(a) 独自コンテキストレイヤ "Teamwork Graph" 上で、要件定義を AI が Confluence の構造化文書として自動生成、(b) 要件から work item を洗い出し、(c) 各 work item の "assignee" として人間だけでなく AI エージェント (Claude Code / GitHub Copilot / Jira 標準 AI エージェント) を指定可能、(d) 計画立案 → agent への委任 → セッション監視を Jira 上で一元化。ベンチマークでは平均トークンコスト -48% を報告。「AI エージェントを PM ツールの "assignee" として 1st class に位置付ける」製品意思決定で、Slack / GitHub Issue に散逸していた agent 監督インタフェースが PM プラットフォームに集約される可能性を示す。

💡読み手のための背景 — (1) "agent を Jira の assignee にする" 設計判断の意味: 従来 agent の起動は「開発者が IDE / CLI から手動 invoke」or「CI が bot として trigger」の 2 系統。Jira assignee 化は "PM が計画段階で agent に task を割り当てる" 第 3 系統 = agent の起動主体が「開発者 / CI」から「PM / EM / プロダクトオーナー」に拡張される。読み手企業で「AI エージェントを誰が起動できるか」の権限議論が Q3 に一気に前進する契機。(2) "Teamwork Graph" が解く問題: 従来の "Jira Issue + Confluence ページ + GitHub PR + Slack 会話" は互いに分断され、agent が判断に必要な context を集めるだけで大量の tool 呼び出し。Teamwork Graph は Atlassian 製品群 (Jira / Confluence / Bitbucket / Compass 等) の全 entity と関係性を単一グラフに集約し、agent が「この issue に関連する要件 / 過去の PR / 参加者の議論」を 1 クエリで取得可能。結果、agent 実行の平均トークンコストが 48% 減 = context を集める query の反復が激減。読み手企業で GraphQL / Knowledge Graph 系の内製プロジェクトがあれば、"agent 用の enterprise knowledge graph 層" の Q4 議論に本記事を叩き台。(3) Claude Code / GitHub Copilot 連携の実務含意: Jira 上で issue に "Claude Code" を assign すると、Jira が指定 repo / branch にジョブを投入し、agent の実行状況 (progress、生成コード、テスト結果) が Jira の issue タイムラインに逆流。従来 Claude Code / Copilot の実行状態は各ツール専用 UI に分散していたのが、Jira 側に統合表示される。読み手企業で「AI エージェント運用の可視性」が Q3 論点なら、Jira を "agent 監督ハブ" として採用する構図が現実解。(4) Linear / Notion / Asana ユーザーへの意味: 本機能は当面 Atlassian エコシステム限定だが、"agent assignee" 概念が業界標準化する signal。Linear / Notion / Asana も Q4-Q1 で同種の機能を追加する可能性大。読み手企業が現在 Jira 以外の PM ツールを使っている場合、Q3 の PoC は "MCP + カスタム bot で assignee ラベルを扱う自作" が現実的。(5) 7/24 briefing 「Copilot canvases」との接続: Copilot canvases = "1 タスク内の agent と人の共有 UI"、Jira Teamwork Graph = "組織全体の agent と人の作業台帳"。両者は排他ではなく "canvas = 実行 surface / Jira = 計画 surface" の階層関係。(6) 汎用化のエッセンス: 2026 後半 = "AI エージェントをどの層 (IDE / CI / PM / Slack) が起動主体になるか" のプラットフォーム争い。Atlassian の先手は PM 層への囲い込み。
