cloudflare/computer v0.2.0 — Durable Object + SQLite を "authoritative state" にした agent 用仮想コンピュータ

🆕新リリース📐設計論Cloudflare
出典: GitHub cloudflare/computer（v0.2.0 リリース: 2026-08-11、週次 Trending +6,807 stars）

Cloudflare が本日 v0.2.0 をリリース。Durable Object 内に SQLite を "authoritative state store" として置き、そこに対して 3 種類の実行 backend（① Container: SQLite state を FUSE mount で射影した Linux userland + 実バイナリ、② Isolate Shell: state store 不要で just-bash を Dynamic Worker 上で実行、③ Isolate JavaScript: durable imports 付き ESM 実行）を workspace.runtime.exec() の単一 API で切り替える。v0.2.0 では egress 設定の統一、RPC 経由の bounded workspace 読み取り、read tool の image / data 対応、find/grep の追加フィルタと delete tool の新設、file chunk リンクによる sync 時ピークメモリ削減が入った。まだ "preview only, NOT for production" だが、"agent に function-call ではなく本物の filesystem + 実行環境を渡す" 設計思想の実装リファレンスとして本命候補。

💡 背景補足: "Durable Object" は Cloudflare Workers の状態を持てる特殊オブジェクトで、単一の永続インスタンスとして振る舞いつつ globally routable な点が特徴。従来 agent に環境を渡すには "Docker コンテナを毎回起動 → shell/exec を露出" が定番だったが、コールドスタートと課金効率が課題だった。SQLite を state の真実として持ち、Container / Isolate を "state への異なる view" として抽象化する設計は、"agent が使う環境" と "永続化される事実" を切り離すエッセンスとして自社実装にも転用可能。

Orca ADE — 1 プロンプトを N 個の agent に並列 fan-out、それぞれ独立 git worktree で走らせて winner を merge

🆕新リリース📐設計論エージェント運用
出典: GitHub stablyai/orca（日次 Trending +881 stars、42,627 stars）

"Agent Development Environment" を名乗り、Codex / Claude Code / OpenCode / Pi など任意の CLI agent を同時に走らせる基盤。設計の中心は "並列 worktree"、すなわち「1 プロンプトを 5 agent に fan-out、それぞれ独立 git worktree で作業させ、diff を比較して勝った実装だけを merge」というワークフロー。加えて Ghostty ベースの WebGL ターミナル（無限 split と再起動を跨ぐ scrollback）、モバイル companion app、SSH worktree（リモートサーバー上の agent を手元から操作）、GitHub / Linear 統合を含む。"1 agent が正解を出すまで待つ" のではなく、"複数 agent の解を並列で得て選ぶ" にワークフローを組み替えるための IDE 相当の存在。

💡 背景補足: 個別 agent の性能競争 (SWE-Bench 何 %) が飽和すると、"1 回の試行の期待値" より "同じコストで N 試行して max を取る" 方式のリターンが増える。git worktree は同じ repo を独立ディレクトリに複数展開する Git 標準機能で、ここに直接 map している点が実装として素直。応用可能なエッセンスは「LLM 呼び出しを "確定的な 1 通" ではなく "並列 sample から選択" として扱うと、下流のマージ・比較・selector 設計が新しい第一級の関心事になる」という点。Claude Code の同時セッション運用にもそのまま持ち込める発想。

Paperclip — 個々のエージェントを "社員"、Paperclip を "会社構造" として扱う組織 OS

🆕新リリース📐設計論エージェント運用
出典: GitHub paperclipai/paperclip（日次 Trending +743 stars、77,082 stars）

Node.js サーバー + React UI で "複数プロバイダの agent を組織的に運用する" ためのプラットフォーム。明確に "agent framework ではなく agent を運用する会社の OS" と位置付けており、4 本柱は (1) チケット制 + 検証ゲート + 監査証跡の Agentic Task Manager、(2) role / permission / delegation を持つ Org Chart for Agents、(3) skills / evals / metrics の Agent Training、(4) multi-provider runtime + 隔離 + secrets + コスト管理の Agentic OS。技術的には atomic task checkout（重複作業防止）、heartbeat 跨ぎの永続状態、runtime での skill 注入、祖先情報付きの goal-aware 実行、1 デプロイ内の multi-company データ隔離を持つ。Cursor / Windsurf のような "個人の IDE" とは真逆で、"agent 群を人と同じ組織構造で扱う" 層の実装例として貴重。

💡 背景補足: Orca が "1 プロンプトの複製実行" の並列化なら、Paperclip は "複数の異なる目的の agent を同時運用" の組織化を狙う（レイヤーが違う）。応用エッセンスは「ticket / org chart / audit trail は人組織のためだけの構造ではなく、agent 群のガバナンスにもそのまま流用できる」という発見で、自社で内製エージェント基盤を作るとき "何を SaaS で買い、何を組織構造として持つか" の判断軸として参考になる。特に "role + budget + approval workflow" を LLM 層でなく orchestration 層で強制する思想は、Cloudflare Wallets（昨日号）と同型の "支払い/権限は payment/governance 層で" 発想。

LoopX — 200 時間規模の長時間 agent タスクを支える "state kernel"、5 質問で loop を運用

🆕新リリース📐設計論エージェント運用
出典: GitHub huangruiteng/loopx（週次 Trending +2,947 stars、Python 3.11+ / MIT）

agent runtime（Codex / Claude Code / Cursor）と実際の実行の間に挟まる軽量な "state kernel"。objective / decisions / evidence / resource quotas を bounded turn を跨いで安定保持し、Kanban に近い抽象で「カードが identity, authority, continuation semantics を運ぶ」形をとる。ループは 5 つの質問で運用: (1) 目的は何か、(2) 次に何が起きるか、(3) 人間の判断が必要か、(4) どの evidence が変わったか、(5) loop を続けてよいか。公開ケースでは 200+ 時間の連続プロジェクト、無人での複数日運用、PR マージ実績を主張。"chat 記憶 + timer だけでは長時間タスクが持続しない" 問題への構造化された答えで、"quota を尊重した auto-wake" と "非エンジニアでも進捗が読める legibility" を両立する設計。

💡 背景補足: 一般的な agent framework は "1 turn の履歴" しか永続化しないため、複数日を跨ぐタスクでは "何を目指していたか" と "何は既に判断済みか" が失われて trajectory drift を起こす。LoopX の "objective / evidence / decision を第一級 record にして turn を跨がせる" 発想は自社で長時間 agent を作るときの必須構造として参考になる。読み替えると「エージェント設計における『データベース設計』の役割は、chat 履歴でも RAG でもなく "5 種類の別テーブル" だ」という主張で、これは LangGraph の checkpoint とも Anthropic の memory とも異なる、専用 kernel を切る側の設計。

firecrawl/pdf-inspector — Rust で "PDF を 10-50ms で分類" してから抽出、200 docs / 0.5s、モデルなし

🛠OSSRustパフォーマンス
出典: GitHub firecrawl/pdf-inspector（週次 Trending +7,143 stars、14,659 stars）

PDF を一律に処理せず、まず content stream をサンプリングして "text-based / scanned / image-based / mixed" の 4 種に 10-50ms で分類し、真の scanned だけを高コスト OCR に回すという設計。ML モデルも外部サービスも使わず pure Rust（依存は lopdf のみ）で 200 documents を 0.5s 未満に処理。Markdown 出力は font size 比の H1-H4 見出し、bullet / numbered / letter リスト、コードブロック、表（rectangle 検出 + heuristic）、bold / italic、URL リンク、ページ区切りに対応。core は Rust だが Python (PyO3) / Node (napi-rs) / Browser WASM binding を持つマルチプラットフォーム。RAG 前処理・ドキュメント OCR コスト最適化・請求書処理のような "大量 PDF が来る" 現場で GPU なし・API 課金なしで前段フィルタとして直接効く。

💡 背景補足: 従来の PDF 抽出は Unstructured.io / LlamaParse のように "全部を高機能パイプに通す" 構成が主流で、OCR API 課金と ML モデルのコールドスタートが実運用の隠れボトルネックだった。pdf-inspector の "まず分類、必要なら OCR" は "早い判定を安く先に置き、高コスト処理を条件付きで発火" という汎用パターンで、これは filterable pre-processing の設計原則そのもの（gate at the cheapest layer that has enough signal）。Rust 単一 crate で Py/Node/WASM を叩ける構成は、"pipeline のホットパスを Rust に切り出しつつ既存 stack を保つ" 実装テンプレートとして参考になる。

AirLLM — GPU 上に "常に 1 レイヤーだけ" 載せる方式で 70B を 4GB VRAM、MoE なら DeepSeek-V3 が 12GB

🛠OSSLLM 推論📐設計論
出典: GitHub lyogavin/airllm（週次 Trending +4,042 stars、30,746 stars）

量子化・蒸留・pruning を一切使わず、モデルをレイヤー単位に分解して "常に 1 レイヤーだけ GPU に載せる" ことで、必要 VRAM を "モデル全体サイズ" ではなく "個々のレイヤーサイズ" に落とす仕組み。素直な結果として 70B モデルが 4GB GPU で動く。sparse MoE モデルでは "レイヤー全体" ではなく "1 エキスパート単位" に更に細分化でき、671B の DeepSeek-V3 でも ~12GB VRAM で推論可能。Llama / Qwen / DeepSeek / Mistral など主要 open LLM を AutoModel 統一 IF で対応。当然レイテンシは上がるので "対話" 用ではなく "ローカルで大きなモデルを触りたい・実験したい・オフラインで動かしたい" 用途向けだが、"評価だけ回したい" 場面の GPU 資源設計を根本から変える選択肢。

💡 背景補足: "モデル全部を VRAM に載せる" は伝統的に inference の暗黙の前提で、この壁を破る手段は主に量子化 (4bit / GGUF) が主流だった。AirLLM の "quantization 不使用でレイヤーごとに載せ替え" は精度を犠牲にしない代わりにレイテンシと引き換える方針で、"精度が要る評価・fine-tune 前の理解・オフライン推論" とは相性が良い。応用エッセンスは「メモリ制約は "モデル全体" ではなく "アクセスパターンの最大単位" で決まる」で、これは CPU cache や DB buffer の設計原則と同型。ローカル LLM のハードウェア要件を "GPU 1 枚のサイズ" から解放する系譜（llama.cpp、Ollama、AirLLM）の中で "精度保持" 側の代表例。

addyosmani/agent-skills — 24 の "senior engineer が使う workflow / quality gate" を Skill 化、Google 由来の Hyrum's Law / Beyonce Rule 明示

🛠OSSClaude Code Skillエンジニアリング組織
出典: GitHub addyosmani/agent-skills（日次 Trending +571 stars、86,169 stars）

Google の Addy Osmani が公開した "production-grade" skill 集。基本思想は「AI コーディングエージェントに shortcut を default で許してはいけない、senior engineer が本番で使う workflow と品質ゲートを skill として明文化する」。ライフサイクル 6 フェーズに 24 skill: Define（interview-me / idea-refine / spec-driven-development）、Plan（planning-and-task-breakdown）、Build（incremental / TDD / context engineering / source-driven / doubt-driven / frontend / API design）、Verify（browser testing with devtools / debugging）、Review（code quality / simplification / security / performance）、Ship（git workflow / CI-CD / deprecation-migration / docs-ADR / observability / launch）+ どの skill をいつ使うかを判断する meta-skill。Hyrum's Law（"contract 未定義の挙動でも利用者は依存する"）や Beyonce Rule（"CI で守らないルールは存在しないと同義"）、trunk-based development を明示的に skill に組み込んでいる点が特徴。

💡 背景補足: Skill Marketplace 系の "skill" は多くが "使い方 tips" レベルだが、agent-skills は "エンジニアリングプラクティスを skill として実装" するアプローチ。応用エッセンスは「暗黙知としてチームで共有してきた品質ゲート（PR 前の TDD、レビューの 4 段階、shipping 前 checklist）は skill として明文化することで agent にも人にも共通の運用基準になる」で、これは onboarding ドキュメントを skill 化する方向の実装例として直接参考にできる。特に doubt-driven-development と source-driven-development は他所であまり見ない概念で、"エージェントが自信過剰にコード書き始めない" ための ISO 的なガードレール。
