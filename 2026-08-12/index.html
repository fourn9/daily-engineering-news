macro-inc/macro — 「会社を computable にする」ための Rust + SolidJS 統合ワークスペース、team-level 記憶とエージェントを 1 st-class 化

🆕新リリース📐設計論エージェント運用
出典: GitHub macro-inc/macro（日次 Trending +325 stars、1,632 stars、Rust + SolidJS、公式サイト macro.com）

email + messages + docs + tasks + agents + calls + CRM を単一の高速インタフェースに統合し、workspace のすべてが @link と bidirectional graph で相互参照される、"team の operating system" を志向するプラットフォーム。前のスタートアップを ~20 名まで伸ばした結果 "各チームが各ツールを持ち、会社は MCP と Zapier で辛うじて繋がって computable ではなくなった" という具体的な失敗経験からの再設計で、2 年間 15 名で自社ドッグフード。設計上重要なのは (1) 各 block（Chat / Docs / Email / CRM 等）は best-in-class を目指して個別実装しつつ、backend は共有で cross-reference が bidirectional graph に native 保存される、(2) agent memory はチャット履歴ではなく、毎晩 cron で email / messages / tasks / docs / calls を横断合成した team-level memory を markdown で保持、(3) MCP surface で内部 UI と 100% 近い機能をカバーし、外部 agent (Claude Code / Codex) も同等操作可能。iOS ネイティブ、CRDT + Cloudflare Durable Objects でリアルタイム共同編集。

💡 背景補足: Notion / Slack / Linear / HubSpot / Superhuman を横断で束ねる "スーパーアプリ" 系は Coda や Fibery が既にあるが、Macro の差別化は「agent を 1 st-class の共同編集者としてバイディレクショナルグラフに乗せる」設計にある。特に "毎晩 memory を synthesize して markdown で持つ" は、agent の "何を覚えているか" を人間が読める場所に置くという発想で、これは chat 履歴ベースの memory (ChatGPT / Claude) や embedding ベースの memory (Mem0) とは別系統。応用エッセンスは「agent-native な workspace は、既存 SaaS の "後付け AI" ではなく "backend の graph 統一 + 夜間 memory 合成" という 2 点をやっているか」で判断できる、という設計指針。

embabel/embabel-agent — Spring 創設者 Rod Johnson による JVM/Kotlin agent framework、GOAP プランナーで OODA loop を回す

🆕新リリース📐設計論JVM/Kotlin
出典: GitHub embabel/embabel-agent（Kotlin、Apache-2.0、Maven Central 公開、docs.embabel.com）

"Spring の生みの親" である Rod Johnson が主導する JVM 上の agentic flow フレームワーク。中核概念は Actions / Goals / Conditions / Domain model / Plan の 5 つ。プランは開発者が書くのではなく非-LLM の AI アルゴリズム（デフォルトはゲーム AI 由来の Goal Oriented Action Planning = GOAP、Utility AI もサポート）が動的に生成し、アクション実行後に毎回 replan する OODA loop 構造をとる。実行モードは 3 段: (1) Focused（コードが特定 agent を明示呼出）、(2) Closed（intent 分類から適切な agent を platform が選ぶ）、(3) Open（platform が既存のすべての goal / action を組み合わせて未プログラムの経路も探索）。annotation ベース (@Agent/@Goal/@Action) と Kotlin DSL の 2 通りで記述可能、Spring と統合され AOP・トランザクション・DI をそのまま活用できる。domain model 経由の strong typing で prompt と手書きコードが magic map なしに繋がる。

💡 背景補足: 現在の agent framework は LangChain (Python) / Vercel AI SDK (TS) / Mastra (TS) など Python/JS が圧倒的多数で、JVM 側は Spring AI と LangChain4j が二強。Embabel の位置づけは「Spring AI の "LLM を呼びやすくする" レイヤより 1 段上に、"何をすべきかを planner に決めさせる" を置く」もの。GOAP は F.E.A.R. で有名になった有限状態機械の上位互換で、"事前条件と事後条件を宣言すれば、既知アクションを未プログラムの順序で組み合わせる" のがエッセンス。JVM 資産（トランザクション、Spring Security、既存の Domain Model）を捨てずに agent 化する道が欲しい既存エンタープライズ、特に金融/保険/物流ドメインで実務に効く選択肢。

NVIDIA-NeMo/Switchyard — OpenAI/Anthropic/OpenAI Responses の 3 API を Rust で相互翻訳する LLM プロキシ、routing 戦略も pluggable

🆕新リリース📐設計論NVIDIA
出典: GitHub NVIDIA-NeMo/Switchyard（Rust、Apache-2.0、pre-alpha、日次 Trending +370 stars）

NVIDIA NeMo チームが公開した LLM トラフィック用 Rust プロキシ + ライブラリ。3 つの API 形式 (OpenAI Chat / Anthropic Messages / OpenAI Responses) を相互翻訳し、Claude Code や Codex のような「特定 API しか話さないコーディングエージェント」を、vLLM / NVIDIA NIM / Ollama / 任意の OpenAI 互換エンドポイントに向けるためのブリッジ。routing 戦略は 4 種を pluggable に提供: (1) LLM Classifier（内容から weak/strong tier を分類）、(2) Stage Router（tool 結果や error などの会話中の signal で決定）、(3) Escalation Router（毎ターンをまず weak で走らせ、judge が strong 送信を判定）、(4) Random（A/B テスト用の固定分割）。3 種の使い方: switchyard launch claude/codex/openclaw のランチャ、switchyard-server のスタンドアロンプロキシ、switchyard-libsy クレートで既存 Rust アプリに埋め込み。Prometheus メトリクス標準対応。

💡 背景補足: 昨日号の Cloudflare/computer が "agent に実行環境を渡す" 層なら、Switchyard は "agent を任意の LLM 提供者に繋ぐ" 層。同種プロダクトに LiteLLM / OpenRouter / Portkey があるが、これらは主に "Python でモデルを差し替える" 用途で、Switchyard は明確に "Claude Code のような特定 API しか話さないバイナリ" を対象にしている点、および routing を "LLM に分類させる" だけでなく "会話中の signal で判定" や "escalation" と抽象化した点が新しい。応用エッセンスは、「エージェントプロキシは pass-through ではなく、"どのモデルにいつルーティングするか" を 1 st-class の関心事として扱う設計に移りつつある」で、コスト最適化 + 品質担保の両立を "エージェント側ではなくプロキシ側で" 決める方向は自社実装でも直接転用可能。

DeepSeek-Reasonix v2 — TS → Go リライトの単一バイナリ、"prefix-cache stability" を invariant として設計したコーディングエージェント

🆕新リリースCoding AgentGo
出典: GitHub esengine/DeepSeek-Reasonix（Go、MIT、週次 Trending +3,517 stars、34,178 stars、npm/brew 配布）

元 TypeScript の Reasonix 0.x（現在は maintenance mode）から Go への完全リライト。設計思想の核は「prefix-cache stability は "後付けの機能" ではなく loop 全体を貫く invariant」というもので、公開ケーススタディでは 2026-05-01 の 1 日で 435M input tokens を 99.82% cache hit 率で処理し、no-cache 想定の 61 ドルが 12 ドルに収まった実測データが載っている。これを支えるのが 4 つの柱: (1) startup で小さな安定した env サマリを注入、(2) stale な tool 出力を summary compaction 前に snip/prune、(3) 内蔵 tool schema contract を regression review 用に文書化、(4) 単一 Go バイナリ (CGO_ENABLED=0) で 6 ターゲットへクロスコンパイル可能。4 つの入口 (TUI / desktop / VS Code 拡張 / ACP プロトコル経由の任意エディタ) が同じローカル engine に繋がる。DeepSeek 特化と明示的に位置付け、"任意モデル対応" を捨てて "1 プロバイダに深く合わせる" 選択。

💡 背景補足: Claude Code / Cursor / Codex は "モデル差し替えが可能" を売りにするが、その代償として prefix cache 契約を保証しづらい。Reasonix の "DeepSeek 専用でよいから、cacheable な bytes を byte-stable に保つ" 発想は、実務コストで数倍差になるトレードオフを "垂直統合で回収する" 側の解答。ACP (Agent Client Protocol) 対応は、Zed が推進中の "エディタと agent runtime の間の標準プロトコル" で、Reasonix v2 は "1 つのローカル engine を CLI / desktop / editor から共有" する ACP model の実例。応用エッセンスは、"どのモデルにも中立" と "特定モデルに合わせて最適化" は同じ関数の異なる解で、後者を選んだ場合の勝ち筋 (byte-stable prefix / 内部 tool の版数管理) が具体的に何を意味するかの参考実装。

Needle 2 — 45M パラメタ / 14MB バイナリ / 28MB RAM でツール呼び出しと構造化抽出、CQ2-bit + Simple Attention Network

🆕新リリースエッジ LLM🔬論文
出典: GitHub cactus-compute/needle（Python、日次 Trending +346 stars、4,120 stars）、arXiv:2607.18363（アーキテクチャ論文）

スマホ / ウェアラブル / スマートホーム / ロボット向けの 45M パラメタモデルで、モデル自体が単一 14MB バイナリに畳み込まれ、フルセッションの実行メモリが約 28MB。同社の Simple Attention Network (SAN) を基盤に CQ2-bit（Cactus 独自 2-bit 量子化）で圧縮し、独自エンジンにベイクイン。ベンチマークでは FunctionGemma 270M / LFM2.5 230M / Apple FM に対し 5〜70x 小さいサイズ / f16 対 2-bit で勝ち負けを分ける水準。SAN の設計要素は (a) FFN の代わりに Hadamard MLP（重みなしで n log n 時間の直交変換）、(b) GQA アテンション、(c) engram key-value memory、(d) multi-lane hyper-connections、(e) 4 residual stream の RMS 正規化＋Sinkhorn による doubly-stochastic ルーティング。振る舞いは "全てを function call として解く": どんな入力もツール呼出か "空配列 []"（=呼べる tool なしの明示的な拒否）、reasoning は unconstrained だが call 自体は byte-level grammar で JSON 破綻がゼロ、confidence 出力で act/escalate を閾値制御。tool retrieval headで大規模カタログの top 5 のみ提示、256 token sliding window + KV sink pinning でメモリ上限を確定。

💡 背景補足: "エッジで動く LLM" の従来のスコープは "会話ができる小さいモデル" だったが、Needle の割り切りは "会話は捨てる、代わりに tool call と構造化抽出だけを保証する" 方向。応用エッセンスは、"モバイル / IoT で LLM を使う" を "LLM をチャットにする" ではなく "LLM を意図パーサ + 引数抽出器にする" と定義し直せば、モデルサイズは 2 桁下げても実務で使えるという設計判断。特に "空配列 []" を「呼べる tool がないときの明示的な返答形式」に組み込んだのは、hallucination 抑制の実装として直接転用できる。デバイス側で完結する tool 呼出は、privacy 要件があるヘルスケア / 金融アプリ、あるいは connectivity 前提を置けないロボットで直に効く。

virgiliojr94/book-to-skill — 技術書 PDF/EPUB を Claude Code / Copilot CLI / Amp の Skill に変換、"Discovery Loop Tax" を 24〜51 倍削減

🛠OSSClaude Code SkillAgent Skills 標準
出典: GitHub virgiliojr94/book-to-skill（Python、MIT、週次 Trending +4,155 stars、20,813 stars）

"買って一度読んで、3 ヶ月後には第 7 章の存在すら忘れている技術書" を、agent がオンデマンドで読める Skill に変換する CLI。/book-to-skill ./book.pdf でファイル / フォルダ / glob を指定すると、SKILL.md（コア mental model + 章インデックス, 約 4K token）、chapters/ch01-*.md（章別、各 ~1K token、呼び出し時のみロード）、glossary.md、patterns.md、cheatsheet.md を生成する。/my-book replication のように呼ぶと agent が該当章だけを読んで実内容から回答するので、"PDF に丸ごと放り込む" 場合の 24〜51 倍のトークン削減（実書で測定）。対応形式は PDF / EPUB / DOCX / MD / HTML / RTF / MOBI で、GitHub Copilot CLI (~/.copilot/skills/)、Amp (~/.agents/skills/)、Claude Code (~/.claude/skills/) が同じ SKILL.md 形式を読める Agent Skills 標準に準拠。書籍以外の使い道として社内 runbook、ブランドガイドライン、RFC、論文クラスタも同じ変換パスに乗る。

💡 背景補足: "PDF を毎回 agent に読ませる" のは、agent が ToC を再フェッチし backtrack し全体を再処理する "Discovery Loop Tax" を毎ターン払うことになる。book-to-skill の勝ち筋は「その構造化コストを変換時に 1 回だけ払い、以後の query は答えに比例したトークンで済む」という時間的分離。応用エッセンスは、"社内ドキュメントは RAG に入れる or vector DB に入れる" だけでなく、"agent の Skill に事前変換する" という第 3 の選択肢があり、章別チャンク + 事前グロッサリ + patterns/cheatsheet の 5 種のファイルを標準化する型が既にオープン標準として存在する、という点。オンボーディングドキュメントや ADR を Skill 化するときの実装テンプレートとして直接参考にできる。

zhaoxuya520/reverse-skill — 41 の routing rule + 163 regression case で AI agent を CTF / リバースエンジニアリング / 脆弱性調査に案内するスキルルータ

🛠OSSセキュリティClaude Code Skill
出典: GitHub zhaoxuya520/reverse-skill（PowerShell + Python、MIT、週次 Trending +6,730 stars、24,418 stars）

"AI agent が APK / ELF / JS 難読化 / PCAP / CTF ターゲットに遭遇したとき、どのツール（jadx / apktool / Frida / IDA / BurpSuite 等）をどの順で使うかを毎回悩んでいる" 状態を解決する Skill パッケージ。中心にあるのは 41 本の routing rule (R0-R40) と、それを守っているかを検証する 163 ケースの regression benchmark、42 の core skill モジュール、Windows + Ubuntu の cross-platform CI。フローは固定型で User task → RULES.md → MASTER-ROUTING (PRIMARY) → case-init / scope.md (auth + network profile; ACT は準備完了まで禁止) → シナリオスキル → tools / MCP / scripts → timeline + Evidence → Finding → Path → report + field-journal。Claude Code / Codex / Cursor / OpenCode のいずれからでも動く "client-neutral" 構成で、認可・ネットワークプロファイルを ACT 前に強制させる ops contract が組み込まれている。

💡 背景補足: セキュリティ調査は "ツール選択の分岐が深いドメイン" で、agent は往々にして「とりあえず strings」「とりあえず jadx」のような近道を取り、証拠チェーンが再現不能になる。reverse-skill が Trending 上位に来ているのは、その意思決定を "41 の明示的なルール" として書き下し、しかも 163 ケースの regression benchmark で崩れないことを CI で担保している点にある。応用エッセンスは、"熟練者の判断ツリー" を暗黙知として放置せず、Skill として明文化し、regression suite で守ることで、agent の "何となく" を減らせる、というアプローチ全般に効く。前日号の addyosmani/agent-skills が "Beyoncé Rule" (CI で守らないルールは存在しない) を掲げていたのと同型で、"skill を CI で守る" が新しい実装標準になりつつある兆し。
